## 1. 왜 만들었나

### 출발점
- SNS에서 **지도에 마커펜(다트)을 던져서 꽂힌 곳으로 여행을 가는 릴스**가 유행했다.
- 친구들끼리 여행을 가고 싶은데 **어디로 갈지 정하지 못하는** 상황이 있었다.
- **유명한 곳만 가기에는 아쉽고**, 조금 **도전적인 여행**을 해보고 싶었다.

### 목표
친구들끼리 여행지를 **재밌고 신박하게** 정하는 서비스.
앱 출시도 고려했지만, 우선 **웹앱**으로 만든다. (설치 없이 링크만으로 친구를 부를 수 있다)

### 콘셉트가 정해진 과정
1. 처음 요청: 다트를 던지고 끝나는 것보다 **재밌는 요소**가 있으면 좋겠다.
2. Claude가 아이템 카드, 실력 요소(조준·힘 조절), 벌칙 룰렛 같은 **게임 장치**를 제안했다.
3. 사용자가 방향을 바로잡았다.
   > "목표를 확실히 정해야겠네, 게임적요소가 아니라 여행지를 고르는 기준, 질문 이런 요소들이 많아져야하는데 이걸 좀 재밌게 하자는거야"
4. 그래서 콘셉트를 이렇게 정했다.
   **"질문에 답할수록 지도가 줄어들고, 남은 땅에 다트를 던진다"**
   - 재미의 중심은 게임 장치가 아니라 **우리만의 여행 기준을 정하는 과정**이다.
   - 다트의 무작위성은 유지하되, 우리가 정한 조건 안에서만 무작위로 고른다.
     덕분에 의외의 동네를 만나면서도 "아무 데나"가 되지 않는다.

## 2. 서비스 결정 (질의응답, 2026-10-29)

## 3. 기술 결정 (Claude 판단, 단 T6의 최종 선택은 사용자)

### T1. Next.js 16 + TypeScript + Tailwind CSS 4
- **이유**
  - 웹앱의 사실상 표준이다.
  - 결과 카드 이미지를 서버에서 만드는 기능이 내장되어 있다.
  - 배포(Vercel)와 궁합이 좋다.
- 작성 시점 최신 안정판인 16.4.3으로 시작했다.
- create-next-app 기본 설정대로 `next.config.ts`에서 Cache Components(`cacheComponents: true`)를 켜 두었다.
  - 그래서 `generateStaticParams` 없이 동적 주소(`/room/[code]`)의 값을 읽는 부분을 `Suspense`로 감쌌다.
  - 이 설정 줄을 지우면 동작이 바뀐다. 버전만으로 켜지는 기능이 아니다.

### T2. 지도: MapLibre GL JS, 배경 지도 타일 없이 경계만 그림
- **이유**
  - 무료 오픈소스라 API 키나 사용량 비용이 없다.
  - 읍·면·동 경계를 직접 칠하고 지우는 연출(P8)을 자유롭게 할 수 있다.
  - 배경 타일이 없으니 게임 같은 단순한 화면이 되고, 외부 지도 서비스에 의존하지 않는다.

### T3. 경계 데이터: vuski/admdongkor `ver20261001` (커밋 고정)
- **이유**
  - 국가데이터처(옛 통계청) SGIS 행정동 경계를 가공한 데이터 중 가장 최신판(2026-10-01 기준)이다.
    - 통계청은 2025-10-01 국가데이터처로 승격됐다. 원본 저장소의 출처 문구는 아직 "통계청"이라서, 이 서비스에서는 "국가데이터처(옛 통계청)"으로 적는다.
  - 상업적 이용도 가능한 라이선스다. 원자료는 공공누리 제1유형, 가공물은 CC BY 4.0이다.
  - 같은 결과를 다시 만들 수 있도록 원본 커밋(`d5d5a82`)을 고정했다.
- **의무**: CC BY 4.0은 출처만이 아니라 **라이선스 링크**와 **변경 사실**도 표시해야 한다.
  - 이 서비스는 경계를 간소화하고 속성을 지웠으므로(T4), 그 사실을 밝혀야 한다.
  - 지도 오른쪽 아래(ⓘ)와 README에 출처, 라이선스 링크, 변경 내용을 넣었다. (처음에는 출처만 넣었다가 2026-10-30 검증에서 보완했다)
- 행정동 기준이라 법정동이 아니라 **행정동 3,559곳**이다.

### T4. 경계 간소화: 5%, 속성은 코드만
- 원본은 약 34MB라 웹에서 쓸 수 없다.
- **속성 제거**: 이름 등 속성이 어느 비율에서든 약 0.5MB를 차지했다.
  - 그래서 경계 파일에는 코드만 남기고, 이름 등은 별도의 지역 목록 파일(`regions.json`)로 분리했다.
- **간소화 비율**: 실측 결과(코드만 남긴 경우)는 아래와 같다.

  | 비율 | 용량 | 압축 전송 |
  |---|---|---|
  | 1% | 약 0.95MB | 약 139KB |
  | 2% | 약 1.09MB | 약 174KB |
  | **5% (선택)** | 약 1.51MB | 약 274KB |

  - 1%로 낮추면 압축 기준 용량이 절반이 된다. 대신 해안선과 작은 동의 경계가 거칠어진다.
  - 이 지도는 다트가 어느 동에 꽂혔는지 판정하는 데도 쓰이므로, **경계 정확도를 우선해 5%를 택했다.**
  - 다만 1%·2%와 화면으로 직접 비교하지는 않았다. 다트 라운드를 만들 때 다시 검토한다 (6장).
- (처음 기록에는 "비율을 낮춰도 용량이 크게 줄지 않는다"고 적었으나, 2026-10-30 검증에서 실측해 보니 틀려서 고쳤다)

### T5. 지역 대표 좌표는 "내부점(inner point)"
- 무게중심은 초승달 모양 지역에서 **경계 밖**으로 나갈 수 있다.
- 거리 계산과 "가장 가까운 유효 읍·면·동"(P6) 판단에 쓸 좌표라서, **원본 경계 기준으로** 항상 지역 안쪽에 있는 점을 썼다.
- **알려진 한계**: 지도와 다트 판정에 쓰는 5% 간소화 경계에서는 3,559곳 중 **11곳**의 대표점이 경계 밖에 놓인다.
  - 해당 지역: 서울 서대문구 북아현동, 양천구 신월6동, 부산 동구 수정1동, 수영구 남천2동, 인천 제물포구 만석동·송림6동, 미추홀구 용현3동, 전남광주통합특별시 동구 동명동, 성남시중원구 은행1동, 광명시 하안2동, 안산시상록구 본오2동
  - 간소화 경계로 대표점의 소속을 판정하는 코드를 만들 때 고려해야 한다 (6장).

### T6. DB·실시간: Supabase → **Convex**로 변경 (2026-10-29)
- **처음 선택: Supabase**
  - Postgres와 실시간 기능이 한 서비스에 있고 무료로 시작할 수 있어서 골랐다.
- **문제**
  - 프로젝트를 만들려고 하니 **무료 프로젝트 한도(2개)**가 이미 차 있었다.
  - 사용자에게 일시정지할 만한 안 쓰는 프로젝트도 없었다.
  - 사용자 요청: "다른 무료 DB 서비스가 있으면 찾아주고, 없으면 기존 프로젝트 같이 쓰기"
- **비교한 선택지**

  | 선택지 | 장점 | 단점 |
  |---|---|---|
  | **Convex** | DB와 실시간이 한 서비스. 무료 플랜 가격 페이지 기준 프로젝트 20개 (문서상으로는 팀당 배포 40개이고, 프로젝트마다 운영·개발 배포를 따로 세므로 혼자 쓰면 약 20개) | 서버 코드를 Convex 방식으로 다시 써야 함 |
  | Neon + Ably | 기존 Postgres SQL을 거의 그대로 사용 | 실시간 기능이 없어 서비스를 하나 더 가입·연결해야 함 |
  | Firebase | 실시간 기본 제공 | 무료 한도를 넘으면 그달 남은 기간 서비스가 꺼짐. 코드도 다시 써야 함 |
  | 기존 Supabase 공유 | 코드 수정이 가장 적음 | 다른 프로젝트와 자원을 나눠 씀. 대시보드 설정 필요 |

- **결정: Convex** (Claude 추천 → 사용자 선택)
  - 서비스 하나로 DB와 실시간을 해결한다.
  - 쿼리가 **구독**이라 데이터가 바뀌면 모든 참여자 화면이 자동으로 갱신된다. 그래서 "변경 알림 + 15초 새로고침" 같은 보조 장치가 필요 없어졌다.
  - 아직 서버 코드가 작아서 바꾸는 비용이 가장 적은 시점이었다.
  - 로컬 백엔드를 띄워 실시간 동작까지 직접 테스트할 수 있었다. Supabase 때는 실시간 서버 이미지를 받지 못해 실시간 동작을 테스트하지 못했다.

### T7. 로그인 없는 참여자 확인: 브라우저가 만든 비밀 토큰 + 서버엔 해시만
- 로그인이 없으므로(P7), 방에 들어올 때 브라우저가 만든 **비밀 토큰**으로 "이 사람이 누구인지"를 확인한다.
- **토큰은 브라우저가 만든다.**
  - Convex의 mutation 안에서 쓰는 난수는 결정적으로 시드되기 때문에, 비밀값을 만드는 데 쓰지 않았다.
- **서버에는 토큰의 SHA-256 해시만 저장하고**, 조회 결과로 절대 내보내지 않는다.
  - DB 내용이 노출되어도 토큰을 알 수 없다.
- 방장만 할 수 있는 동작(출발지 변경 등)은 서버 함수 안에서 토큰으로 방장인지 확인한다.

### T8. 방 코드: 6자리, 헷갈리는 문자 제외
- 친구에게 말로 불러주거나 직접 입력할 수 있게 짧게 만들었다.
- 0/O, 1/I/L처럼 헷갈리는 문자는 뺐다. 31개 문자 × 6자리로 약 8.9억 가지다.
- 코드는 비밀이 아니라 공유용이라 일반 난수로 충분하다.
  - 진짜 비밀은 T7의 토큰이 맡는다.

### T9. 한 방 최대 8명 (임시값)
- 한 명씩 차례로 다트를 던지는 구조라서, 인원이 많을수록 한 판이 길어진다.
- 친구 여행 인원을 고려해 8명으로 정했다.
- 근거가 강한 값은 아니라서 써보고 조정한다.
- 동시에 여러 명이 들어와도 정원과 차례 번호가 지켜지는지 테스트했다. 9명이 동시에 참여하면 8명만 들어가고, 차례 번호도 겹치지 않았다.

### T10. 접속 표시: 30초 하트비트, 75초 안에 신호가 있으면 접속 중
- **무료 한도를 아끼기 위해** 간격을 길게 잡았다.
  - Convex 무료 플랜은 함수 호출 수에 한도가 있고, 하트비트와 그 때문에 다시 실행되는 쿼리도 호출 수에 포함된다.
- **접속 기록을 방 정보와 별도 테이블에 저장한다.**
  - 하트비트가 올 때마다 방 화면 전체가 다시 계산되지 않게 하기 위해서다.
- **접속 여부는 브라우저가 현재 시각과 비교해서 판단한다.**
  - Convex 쿼리는 읽은 데이터가 바뀔 때만 다시 실행되고, 시간이 흐르는 것만으로는 다시 실행되지 않는다.
    그래서 서버에서 "지금 시각"으로 판단하면 결과가 오래된 채로 남을 수 있다. (공식 문서도 쿼리 안에서 `Date.now()`를 쓰지 말라고 권한다)
- 화면이 숨겨져 있을 때는 신호를 보내지 않는다.
- 새로고침 등으로 신호가 몰려도 15초 안의 중복 신호는 저장하지 않는다.

### T11. 출발지: 주요 역 7곳 바로가기 + 읍·면·동 검색
- 사람들은 출발지를 보통 "서울역"처럼 **역 이름**으로 떠올린다.
- 그래서 자주 쓰는 역을 바로가기로 두고, 나머지는 우리가 가진 읍·면·동 목록에서 검색하게 했다.
  - 외부 주소 검색 API가 필요 없다.
- 역 좌표는 직접 넣은 값이라 수백 m 오차가 있을 수 있다.
  - 거리 기준은 직선거리로 대략 판단하는 용도라 영향이 거의 없다.
- **검색 정렬**: 동네 이름이 직접 맞는 결과를 먼저 보여준다.
  - 테스트에서 "성산"을 검색하니 "창원시성산구 ○○동"이 먼저 나와 "성산읍"이 목록에서 밀려나는 문제를 발견해 고쳤다.

### T12. 거리 기준은 우선 직선거리 (예정)
- 출발지에서 약 3,500개 동까지의 실제 이동 시간을 매번 길찾기로 계산하기는 어렵다.
- 그래서 처음에는 직선거리 구간으로 대략 판단하고, 길찾기 API 보정은 3단계로 미룬다.

### T13. 여행 인프라는 미리 집계 (예정)
- 한국관광공사 TourAPI를 게임 중에 실시간으로 부르지 않는다.
- 미리 읍·면·동별 숙소·식당·관광지 개수를 집계해 둔다.
- 그러면 게임 속도가 외부 API에 좌우되지 않고 호출 한도도 아낄 수 있다.

### T14. 다트 착지 지점은 서버에서 계산 (예정)
- 모든 참여자가 같은 결과를 보고, 특정 참여자가 결과를 조작하지 못하게 하기 위해서다.

### T15. 글꼴은 시스템 글꼴
- 외부 웹 글꼴을 내려받지 않고 기기 기본 한글 글꼴을 쓴다.
  - 우선순위: Pretendard → Apple SD Gothic Neo → Noto Sans KR → 맑은 고딕
- 로딩이 빠르고 빌드할 때 외부 다운로드가 필요 없다.

## 5. 개발 과정에서 있었던 일

- **Supabase 로컬 테스트 실패**
  - 실시간 서버 이미지를 Docker Hub와 AWS 양쪽 모두 다운로드 한도에 걸려 받지 못했다.
  - 그래서 Postgres와 API만 따로 띄워 테스트했고, 실시간 동작은 확인하지 못했다.
- **Convex 로컬 테스트 우회**
  - 이 작업 환경에서는 Convex CLI가 쓰는 버전 확인 주소가 네트워크 정책으로 막혀 있었다.
  - 그래서 백엔드 실행 파일을 GitHub 릴리스에서 직접 받아 띄워 테스트했다.
  - 사용자 PC에서는 이런 제한이 없으니 `npx convex dev`만으로 동작할 것으로 예상한다. (아직 사용자 PC에서는 확인 전)
- **테스트로 찾아 고친 문제**
  - Supabase 시절: rooms↔players 관계가 둘이라 조회가 실패하던 문제
  - 방 코드 입력칸의 안내 문구 글자 간격이 너무 넓던 문제
  - 지도 출처 문구가 지도를 가리던 문제
  - 동네 검색 정렬 문제 (T11)
- **결정 기록 검증 (2026-10-30)**
  - 이 문서를 독립된 검증 3개로 확인했다: 코드 대조, 외부 사실(웹), 문서 간 일관성.
  - 고친 것
    - T4 용량 비교 오류 (실측으로 정정)
    - 라이선스 표시 보완: 라이선스 링크와 변경 사실 추가 (T3)
    - 기관명 갱신: 통계청 → 국가데이터처(옛 통계청)
    - Cache Components 설명 (T1), 토큰을 만드는 쪽 표현 (T7), 쿼리 재실행 설명 (T10), Convex 무료 한도 표현 (T6)
    - 설계 문서·README와 어긋나던 부분 (상태 표시, 데이터 구조, 로드맵 단계)
  - 새로 알게 된 한계: 간소화 경계에서 대표점 11곳이 경계 밖 (T5)
